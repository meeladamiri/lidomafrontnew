# وضعیت رزرو و تغییر دستی آن

`backend/src/modules/reservations/stateChange.service.ts` ·
`front/components/Admin/ReservationStatePanel.tsx`

## شش وضعیت — از خود اودو

`sale_order.x_temp_state` («وضعیت کمکی») دقیقاً همین‌ها را داشت:

| اودو | تعداد | ما |
|---|---|---|
| `draft` | ۷۱۶ | **اضافه شد** |
| `host_approval` | ۵۳٬۴۱۸ | از قبل |
| `second_payment` | ۱۷٬۹۴۸ | از قبل |
| `done` | ۱٬۲۳۲ | از قبل |
| `cancel` | ۱٬۱۴۷ | از قبل |
| `expired` | ۲۴۶ | از قبل |

`DRAFT` («در انتظار ثبت درخواست») تنها موردی بود که نداشتیم، و نبودش یعنی
پشتیبانی راهی نداشت رزروی را توصیف کند که وجود دارد ولی هنوز جایی فرستاده نشده.
**هیچ‌چیز خودکار آن را نمی‌سازد** — فقط دستی قابل انتخاب است، همان‌طور که در اودو بود.

## مشکل قبلی

پنل فقط می‌توانست رزرو را **جلو** ببرد، هر مرحله یک دکمه. کسی که اشتباهی رزروی را
جلو می‌برد **راهی برای برگرداندنش نداشت**. و هیچ‌جا نمی‌پرسید **چرا** — یعنی
ستون وضعیت می‌گفت رزرو کجاست و هیچ‌چیز نمی‌گفت چطور به آنجا رسیده.

## حالا

هر تغییر دستی **توضیح اجباری** می‌گیرد (حداقل ۳ کاراکتر، در خود schema نه فقط در
فرم — دلیلِ اختیاری، دلیلی است که خالی می‌ماند) و در
`reservation_state_changes` با نام کاربر ثبت می‌شود. نام **کپی** می‌شود نه join،
چون ردیف باید بعد از تغییر نام یا حذف حساب هم بگوید چه کسی این کار را کرده.

**تغییرهای خودکار هم لاگ می‌شوند** — انقضا و لغو. تایم‌لاینی که فقط کارهای آدم‌ها
را نشان بدهد و حرکت‌های خود سیستم را جا بیندازد، طوری خوانده می‌شود که انگار بینشان
هیچ اتفاقی نیفتاده.

## چه تغییرهایی مجاز است

```
DRAFT            → HOST_APPROVAL
HOST_APPROVAL    → DRAFT · SECOND_PAYMENT · EXPIRED
SECOND_PAYMENT   → HOST_APPROVAL · DONE · EXPIRED
DONE             → SECOND_PAYMENT
EXPIRED          → HOST_APPROVAL · SECOND_PAYMENT
CANCEL           → (هیچ‌کدام)
```

جلو و عقب در مسیر خودِ رزرو، چون **اصلاح اشتباه** دلیل وجود این قابلیت است.

دو قاعده عمدی:

- **از `CANCEL` خارج نمی‌شود.** لغو، پول را به مهمان برمی‌گرداند، درآمد میزبان را
  پس می‌گیرد و بدهی پنل واریزی را بازنویسی می‌کند. برگرداندن رزرو یعنی همه‌ی آن‌ها
  باید بازگردانده شوند، و بی‌صدا انجام‌نشده رهاکردنشان همان‌جایی است که میزبان
  دوبار پول می‌گیرد. به‌جایش رزرو جدید ثبت شود.
- **از این فرم به `CANCEL` نمی‌رود.** لغو به لغوکننده، موجه‌بودن و انتخاب
  اطلاع‌رسانی نیاز دارد که یک «توضیح» نمی‌تواند حملشان کند — پس فرم خودش را دارد.
  ولی `CANCEL` عمداً در enum ورودی مانده تا سرویس بتواند **جمله‌ی راهنما** بدهد؛
  حذفش از enum فقط «ورودی نامعتبر است» تولید می‌کرد که به اپراتور چیزی نمی‌گوید.

## عوارض هر وضعیت واقعاً اعمال می‌شود

این مهم‌ترین بخش است. رزروی که دستی به «قطعی» کشیده می‌شود باید **دقیقاً همان
پولی را به میزبان بدهد** که مسیر عادی می‌دهد، وگرنه پنل تبدیل می‌شود به راهی برای
ساختن رزروهایی که حساب‌وکتاب خبردار نمی‌شود.

| وضعیت مقصد | چه اتفاقی می‌افتد |
|---|---|
| `HOST_APPROVAL` | مهلت تایید از تنظیمات دوباره ست می‌شود |
| `SECOND_PAYMENT` | مهلت پرداخت ست می‌شود · اعلان «تایید شد» |
| `DONE` | مبلغ پرداختی کامل · مهلت پاک · **سهم میزبان مسدود واریز می‌شود** |
| `DRAFT` / `EXPIRED` | مهلت پاک · **تقویم آزاد می‌شود** |

⚠️ ست‌کردن دوباره‌ی مهلت اهمیت دارد: رزروی که به «در انتظار تایید میزبان»
برگردانده شود با مهلت گذشته، بلافاصله در اجرای بعدی زمان‌بند دوباره منقضی می‌شد.

و رفت‌وبرگشت بین «پرداخت مهمان» و «قطعی» **دوبار پول نمی‌دهد** — قبل از واریز،
وجود `BOOKING_INCOME` همان رزرو چک می‌شود.

## تست روی سرور

| | |
|---|---|
| `HOST_APPROVAL → DRAFT` | ✓ عقب‌گرد کار می‌کند |
| `DRAFT → DONE` | رد شد: «تغییر وضعیت از «در انتظار ثبت درخواست» به «قطعی» مجاز نیست» ✓ |
| مسیر کامل تا `DONE` | ✓ کیف پول میزبان: ۱ ردیف `BOOKING_INCOME` مسدود |
| `→ CANCEL` | رد شد با جمله‌ی راهنما ✓ |
| توضیح خالی / ۲ کاراکتری | رد شد ✓ |
| رفت‌وبرگشت `DONE ↔ SECOND_PAYMENT` | همچنان ۱ ردیف درآمد — دوبار پرداخت نشد ✓ |
| تاریخچه | چهار ردیف با متن، تاریخ و نام ادمین ✓ |

## چه چیزی هنوز نیست

- **جریان ساخت رزرو هنوز از `HOST_APPROVAL` شروع می‌شود**، نه `DRAFT`. عوض‌کردنش
  رفتار مهمان را تغییر می‌دهد و درخواست نشده بود؛ اگر لازم شد، یک خط است.
- `ReserveStates_enum` فرانتِ عمومی هنوز `draft` را ندارد (فقط پنل ادمین دارد).

# کیف پول و تسویه

`backend/src/modules/wallet/` · `front/components/Wallet/` · `front/pages/admin/wallet/`

## نقطه‌ی شروع: همان الگوی اعلانات

`/api/wallet` وجود نداشت. فرانت سه اندپوینت مرده‌ی Odoo را صدا می‌زد —
`users/panel/wallet`، `users/save_bank_info`، `submit_clearing_req` — و فقط
toast خطا نشان می‌داد. سربرگ خودِ `schema.prisma` هم این را زیر «فاز ۲، هنوز
مدل نشده» فهرست کرده بود.

## مدل داده

مهاجرت: `20260830030000_wallet` — سه enum، سه جدول، صفر دستور مخرب.

```
wallets              balance · blocked_balance · gift_balance
wallet_transactions  kind · status · amount · balance_after · description
settlement_requests  amount · status · اسنپ‌شات بانکی · admin_note
```

### موجودی سه‌بخشی است چون قواعدش فرق دارد

| | |
|---|---|
| `balance` | قابل برداشت همین الان |
| `blocked_balance` | کسب شده ولی اقامت هنوز نشده؛ لغو باید بتواند پسش بگیرد |
| `gift_balance` | خرج می‌شود، هرگز برداشت نمی‌شود |

این سه، سه برچسب روی یک عدد نیستند.

## چهار تصمیم که برای پول اهمیت دارند

**۱. دفتر فقط افزوده می‌شود.** اصلاح، یک ردیف جدید است نه ویرایش یک ردیف قدیمی.
پس هر جابه‌جایی پول دلیل، نویسنده و زمان دارد. **هیچ اندپوینت ادمینی مستقیم
موجودی نمی‌نویسد** — حتی `adjust` هم یک تراکنش است.

**۲. موجودی ذخیره می‌شود، ولی فقط داخل همان transaction دیتابیسی که ردیف دفتر
را می‌نویسد.** پس نمی‌توانند از هم جدا بیفتند. دلیل ذخیره‌کردن به‌جای جمع‌زدن:
این عدد در هر لود صفحه‌ی کیف پول خوانده می‌شود، و جمع‌زدن کل تاریخچه‌ی یک میزبان
هر ماه کندتر می‌شود.

**۳. درخواست تسویه، موجودی را فوراً کسر می‌کند** — در همان transaction که
درخواست را می‌نویسد. اگر تا زمان تأیید ادمین صبر می‌کرد، یک میزبان می‌توانست
همان موجودی را دوبار درخواست کند و دوبار طلبکار شود؛ و **درخواست دوم در لحظه‌ی
ثبت کاملاً معتبر به نظر می‌رسید**.

به همین دلیل `REJECTED` یک وضعیت است نه حذف: رد کردن پول را برمی‌گرداند و دفتر
باید این رفت‌وبرگشت را نشان دهد.

**۴. اطلاعات بانکی هنگام ثبت درخواست کپی می‌شود.** میزبانی که بعد از درخواست
کارتش را عوض می‌کند نباید بی‌صدا پرداختی را که در جریان است منحرف کند، و سند
باید نشان دهد پول واقعاً کجا رفت.

## درآمد میزبان

به تنها جایی وصل است که یک رزرو `DONE` می‌شود (`admin.service.ts`).

- مبلغ از `Reservation.hostShare` می‌آید که از مهاجرت Odoo آمده و **از کمیسیون
  کسر شده**. بازمحاسبه‌اش اینجا دقیقاً همان‌جایی است که دو عدد شروع به اختلاف
  می‌کنند.
- **مسدود** وارد می‌شود نه قابل‌برداشت: رزرو پرداخت شده ولی اقامت هنوز نشده.
- برخلاف hookهای چت و اعلان، این یکی `await` می‌شود. **این پول است**؛ اگر
  نوشتن شکست بخورد، کامل‌کردن رزرو هم باید شکست بخورد تا این دو از هم جدا نیفتند.

`releaseMaturedEarnings()` مسدود را به قابل‌برداشت می‌برد وقتی مهمان رفته.
جدا شده چون **بر اساس تاریخ اتفاق می‌افتد نه بر اساس یک عمل**.

⚠️ **زمان‌بند (cron) در این پروژه وجود ندارد.** فعلاً از پنل صدا زده می‌شود:
`POST /api/admin/wallet/release-matured`. idempotent است، پس اجرای دوباره در یک
روز فقط یک کوئری هزینه دارد.

## اندپوینت‌ها

**کاربر** — `GET /api/wallet` · `GET /transactions` · `PUT /bank-account` ·
`GET /settlements` · `POST /settlements`

**ادمین** — `GET /settlements` · `POST /:id/approve|paid|reject` ·
`GET /users/:id` · `POST /users/:id/adjust` · `POST /release-matured`

شماره کارت (۱۶ رقم) و شبا (۲۴ رقم) در بک‌اند اعتبارسنجی می‌شوند، نه فقط در UI —
این عددی است که پول به آن فرستاده می‌شود.

## پنل ادمین

`/admin/wallet` — صف تسویه. فیلتر وضعیت، تأیید، پرداخت‌شده، رد.

**رد کردن دلیل اجباری دارد** چون موجودی را برمی‌گرداند و همان دلیل به میزبان
نشان داده می‌شود؛ بدون آن، هر رد یک تیکت پشتیبانی می‌شود.

در فهرست فقط **چهار رقم آخر کارت** رندر می‌شود. شماره‌ی کامل در سند می‌ماند برای
کسی که انتقال را انجام می‌دهد، نه در فهرستی که روی یک مانیتور مشترک باز است.

## فرانت

| | |
|---|---|
| صورت‌حساب | cursor-based از سرور. قبلاً کل تراکنش‌ها یکجا در پاسخ کیف پول می‌آمد و در حافظه صفحه‌بندی می‌شد — برای حساب تازه خوب، برای میزبانی که دو سال است اجاره می‌دهد نه |
| کارت تراکنش | می‌گوید پول آمده یا رفته. کارت قبلی فقط «موفق/ناموفق» می‌دانست و همیشه «واریز به: …» می‌نوشت، چون اندپوینت Odoo چیز دیگری نمی‌داد |
| علامت | با کلمه («+» / «−» جداگانه) نه یک `-` چسبیده — روی خط راست‌به‌چپ، منفیِ ابتدای عدد جایی می‌افتد که کسی دنبالش نمی‌گردد |
| برگه‌ی تسویه | مبلغ می‌گیرد. برگه‌ی قبلی هیچ مبلغی نمی‌فرستاد و سرور تصمیم می‌گرفت؛ میزبانی که می‌خواست بخشی از موجودی را بردارد راهی برای گفتنش نداشت |

### دکمه‌ای که حذف شد

«افزایش موجودی کیف پول» و مودالش برداشته شدند. به `api/Payment` وصل بودند و
**درگاه پرداختی وجود ندارد** — خود `admin.service.ts` این را در کامنت نوشته.
دکمه‌ای که نمی‌تواند کارش را بکند از نبودنش بدتر است: یک قابلیت غایب را به یک
قابلیت خراب تبدیل می‌کند.

## تست چرخه‌ی کامل روی سرور

مسیر پول است؛ «کامپایل شد» کافی نیست.

| گام | نتیجه |
|---|---|
| ادمین ۵۰۰٬۰۰۰ واریز کرد | موجودی ۵۰۰٬۰۰۰ ✓ |
| میزبان ۲۰۰٬۰۰۰ تسویه خواست | موجودی **فوراً** ۳۰۰٬۰۰۰ ✓ |
| درخواست دوم | رد شد: «یک درخواست تسویه در حال بررسی دارید» ✓ |
| صف ادمین | `#1 · ۲۰۰٬۰۰۰ · کارت ••••7890` ✓ |
| ادمین رد کرد | موجودی به ۵۰۰٬۰۰۰ برگشت ✓ |
| کارت `123` | «شماره کارت باید ۱۶ رقم باشد» ✓ |

دفتر نهایی — دقیقاً همان رفت‌وبرگشتی که طراحی شده بود:

```
+ ۵۰۰٬۰۰۰  DONE    موجودی=۵۰۰٬۰۰۰  اصلاح حساب (توسط ادمین #1)
− ۲۰۰٬۰۰۰  FAILED  موجودی=۳۰۰٬۰۰۰  درخواست تسویه ← دلیل رد
+ ۲۰۰٬۰۰۰  DONE    موجودی=۵۰۰٬۰۰۰  بازگشت مبلغ تسویه رد شده
```

## چه چیزی هنوز نیست

- **درگاه پرداخت** — بدون آن، شارژ کیف پول ممکن نیست.
- **زمان‌بند** برای `releaseMaturedEarnings`.
- `/admin/comments` و `/admin/statistics` هنوز لینک‌های شکسته‌ی سایدبارند
  (`/admin/transactions` به همین صفحه وصل شد).

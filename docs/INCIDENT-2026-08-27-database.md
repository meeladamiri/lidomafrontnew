# حادثه — پاک‌شدن دیتابیس، ۲۰۲۶-۰۸-۲۷

## خلاصه

دیتابیس اپ روی `lidoma-db` کاملاً پاک شد. از بکاپ روزانه‌ی لیارا بازیابی شد. **حدود ۱۵ ساعت داده از دست رفت** (۰۳:۱۶ تا ۱۸:۴۵ همان روز).

## علت

این دستور اجرا شد تا SQL مهاجرت جدید با خروجی خود Prisma مقایسه شود:

```bash
npx prisma migrate diff --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url "$DATABASE_URL"      # ← دیتابیس زنده
```

`--from-migrations` برای بازپخش مهاجرت‌ها یک دیتابیس موقت لازم دارد، و **Prisma هرچه به‌عنوان shadow database بگیرد را اول کاملاً پاک می‌کند**. آدرس دیتابیس زنده به آن داده شد.

نتیجه: `public` schema در دیتابیس `postgres` drop و از روی مهاجرت‌ها بازساخته شد. ۴۹ جدول خالی، `_prisma_migrations` ناپدید.

## قاعده‌ای که از این به بعد باید رعایت شود

**هیچ‌وقت `--shadow-database-url` را به یک دیتابیس که داده دارد ندهید.** اگر مقایسه‌ی مهاجرت لازم شد، از `--from-empty` استفاده کنید که هیچ دیتابیسی نمی‌خواهد:

```bash
npx prisma migrate diff --from-empty \
  --to-schema-datamodel prisma/schema.prisma --script
```

همان کار را انجام می‌دهد و به هیچ سروری وصل نمی‌شود.

## چه چیزی سالم ماند

`odoo_legacy` — دیتابیس منبع Odoo، ۱۵ گیگ، روی همان اینستنس. دستور فقط دیتابیس `postgres` را هدف گرفته بود.

این مهم بود: حتی اگر بکاپ در دسترس نبود، `scripts/migrate-odoo-*.ts` می‌توانستند همه‌چیز را از نو بسازند (به‌جز محتوای CMS که در پنل ساخته شده و از Odoo نیامده). فایل‌های نگاشت `scripts/image-map.json` و `host-avatar-map.json` هم لوکال موجود بودند.

## نکته‌ای که بدون شک کاربر پیدا نمی‌شد

کاربر پرسید «مطمئنی پاک شده؟ پنل می‌گوید ۴۰٪ پر است.» آن ۴۰٪ `odoo_legacy` بود، نه دیتابیس اپ — که ۱۴ مگ شده بود. همان سؤال بود که `odoo_legacy` را کشف کرد.

**درس:** وقتی نشانه‌ای با تشخیص نمی‌خواند، نشانه را جدی بگیرید نه تشخیص را.

## بازیابی

بکاپ روزانه‌ی لیارا، `2026-08-27 03:38` (۷.۸۸ گیگ). آرشیو دو دامپ جدا داشت:

```
odoo_legacy.dump   ۸.۴۸ گیگ   ← لازم نبود، منبع سالم بود
postgres.dump      ۳۸ مگ      ← تنها چیزی که باید برمی‌گشت
```

ریستور پنل لیارا همیشه در یک سرویس **جدید** انجام می‌شود، نه در جای خودش. به‌جایش دستی انجام شد:

```bash
pg_restore --clean --if-exists --no-owner --no-privileges \
  -d "<connection-string>" postgres.dump
```

`pg_restore` نسخه‌ی ۱۸ لازم بود (مبدأ PostgreSQL 18.0). روی سیستم نصب نبود ولی **PostgreSQL Maestro آن را همراه دارد**:

```
C:\Program Files (x86)\SQL Maestro Group\PostgreSQL Maestro\x64\pg_restore.exe   → 18.0
```

(نسخه‌ی ۳۲ بیتی کنارش ۱۳.۱ است و دامپ ۱۸ را نمی‌خواند.)

⚠️ باینری‌های ویندوزی مسیر فارسی را نمی‌خوانند — فایل باید به مسیر انگلیسی کپی شود.

| بخش | بعد از ریستور | ثبت‌شده در PROGRESS |
|---|---|---|
| کاربران | ۲۸۶٬۵۲۷ | ۲۸۶٬۵۲۷ ✓ |
| اقامتگاه‌ها | ۹٬۵۷۳ | ۹٬۵۷۳ ✓ |
| رزروها | ۲۹٬۶۵۰ | ۲۹٬۶۴۹ ✓ (یکی جدیدتر) |
| نظرات | ۹٬۴۲۷ | ۹٬۴۲۷ ✓ |
| مکان‌ها | ۵۶۵ | ۵۶۵ ✓ |
| لینک امکانات | ۱۵۰٬۰۶۶ | ۱۵۰٬۰۶۶ ✓ |

**سکانس‌ها** مهم‌ترین چیزی بودند که می‌توانستند بی‌صدا خراب بمانند — همه جلوتر از بیشترین `id`، پس ثبت‌نام یا رزرو جدید با کلید تکراری برخورد نمی‌کند.

۲۴ خطای ریستور همه از فاز `--clean` بودند («نمی‌توان drop کرد، وابستگی دارد») و صفر خطا روی داده.

## نکته‌ی مهاجرت بعد از ریستور

بکاپ قدیمی‌تر از مهاجرت `conversations` بود، ولی جدول‌هایش از بازسازیِ shadow روی دیتابیس مانده بودند — پس `migrate deploy` با «type already exists» شکست خورد.

راه‌حل **بدون حذف چیزی**:

```bash
npx prisma migrate resolve --applied 20260827160000_conversations
npx prisma migrate deploy
```

چون همان مهاجرت آن جدول‌ها را ساخته بود، ساختار از قبل یکی بود.

## آنچه باید یاد گرفته شود

۱. `--shadow-database-url` روی دیتابیس واقعی هرگز.
۲. جدول آمار داده در `PROGRESS.md` — همان چیزی بود که درستی ریستور را قابل سنجش کرد. به‌روز نگه‌داشتنش ارزش دارد.
۳. `archive_mode` روی این اینستنس خاموش است و فقط ۵ فایل WAL نگه داشته می‌شود، یعنی point-in-time recovery ممکن نیست. تنها راه بازگشت، بکاپ روزانه‌ی لیاراست.

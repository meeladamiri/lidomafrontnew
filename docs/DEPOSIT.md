# پنل واریزی (`/deposit`)

`backend/src/modules/deposit/` · `front/api/Deposit/` · `front/components/Deposit/`

## نقطه‌ی شروع: صفحه‌ای که کامل بود و به هیچ‌جا وصل نبود

`front/pages/deposit` و ۲٬۳۴۱ خط کامپوننتش همراه بقیه‌ی سایت مهاجرت کرده بودند
و **هفت اندپوینت اودو** را صدا می‌زدند که در بک‌اند جدید هیچ‌وقت ساخته نشده
بودند. همان الگوی اعلانات و کیف پول، برای سومین بار.

| اندپوینت اودو | حالا |
|---|---|
| `internal/has_permission` | `GET /api/deposit/permission` |
| `internal/get_checkouts` | `GET /api/deposit/checkouts` |
| `internal/save_settle_info` | `POST /api/deposit/settle` |
| `internal/save_batch_settle` | `POST /api/deposit/batch-settle` |
| `internal/update_remainder` | `PATCH /api/deposit/:id/remainder` |
| `internal/save_sale_desc` | `PATCH /api/deposit/:id/description` |
| `internal/save_bank_info` | `PUT /api/deposit/hosts/:id/bank` |

## UI دست نخورد

فقط لایه‌ی `api/Deposit/*.ts` عوض شد: اندپوینت‌های جدید را صدا می‌زند و جواب را
به همان پاکت JSON-RPC اودو (`result: "success"` / `err_msg`) برمی‌گرداند که
کامپوننت‌ها بلدند. صفحه‌ای که ماه‌ها وقت برده، برای عوض‌کردن مخاطبش بازنویسی
نشد.

**تبدیل تاریخ جلالی هم همین‌جا انجام می‌شود.** تقویم پنل «۱۴۰۵/۰۶/۰۸» تولید
می‌کند چون کاربرش همین را می‌خواند؛ بک‌اند همه‌جا ISO است، و یک اندپوینت که
بی‌صدا تقویم دیگری انتظار داشته باشد تله‌ای است برای نفر بعدی.

## سه روش تسویه، و چرا یکی نشدند

| | |
|---|---|
| **مانده واریز** | پرداخت باقی‌مانده |
| **واریز بیعانه** | پرداخت بخشی، جلوتر از موعد |
| **کسر بدهی میزبان** | بدهی میزبان به ما در برابر طلبش تهاتر می‌شود — **هیچ پولی از بانک خارج نمی‌شود** |

اگر هر سه «خروج پول» حساب می‌شدند، سومی یک واریز جعلی در گزارش بانکی می‌ساخت.

و **ویرایش مانده واریز** اصلاً پرداخت نیست: یک اصلاح است، با دلیل اجباری، که در
تاریخچه به‌صورت `remainder_update` ثبت می‌شود. مقدار ثبت‌شده **تغییر** است نه
عدد جدید — لاگی که بنویسد «شد ۵۰۰٬۰۰۰» نمی‌گوید قبلش چه بود.

## `clearRemainder` چرا ستون است نه تفریق

می‌شد `hostShare − settledAmount` حساب کرد. ولی تیم مالی می‌تواند این عدد را با
دلیل بازنویسی کند، و از آن لحظه دو عدد به‌درستی با هم فرق دارند — و آنکه درست
است همان override است. تفریق‌کردن یعنی بی‌صدا دور ریختن اصلاحی که کسی عمداً
انجام داده.

## دو دفتر که عمداً یکی نشدند

| | |
|---|---|
| `Reservation.clearRemainder` | چقدر بابت **این رزرو** به میزبان بدهکاریم. موضوع این پنل همین است |
| `Wallet` | موجودی میزبان در **این سیستم**، که فقط برای رزروهای تکمیل‌شده‌ی همین‌جا وجود دارد |

پس هر پرداخت همیشه مانده‌ی رزرو را جابه‌جا می‌کند، و کیف پول را **فقط وقتی** که
واقعاً آن پول را نگه داشته. اگر کیف پول اجباری می‌شد، پنل هر ردیف مهاجرت‌شده از
اودو را رد می‌کرد (یعنی امروز همه‌شان را)؛ و اگر بی‌حساب واریز می‌کرد، پولی
می‌ساخت که هرگز وجود نداشته.

## مهاجرت داده — بدون آن پنل خطرناک بود

اولین بار که پنل بالا آمد، **۲۹٬۰۴۶ رزرو با کل سهم میزبان طلبکار** نشان داده
می‌شدند؛ پولی که اودو سال‌ها پیش پرداخت کرده بود. تیم مالی با خواندن آن فهرست
دوباره پرداخت می‌کرد.

`scripts/migrate-odoo-deposits.ts` این را از دو جدول اودو می‌آورد:

| | |
|---|---|
| `x_clear_remainder_info` | لاگ تغییرات «مانده واریز» — جدیدترین ردیف هر سفارش، مقدار امروز است |
| `wallet_transaction` (debit) | خود پرداخت‌ها |

⚠️ **نکته‌ای که اول اشتباه رفتم:** اول فقط روی لاگ مانده حلقه زدم و ۷٬۰۸۳ رزرو
درآمد. چون فقط **۸٬۰۹۶** سفارش از ۴۳٬۹۳۹ سفارش قطعی اصلاً ردیف لاگ دارند، در
حالی که **۳۴٬۸۶۶** تا پرداخت دارند. حلقه باید روی رزروهای خودمان بزند، نه روی
لاگ — وگرنه بیشتر رزروها پرداخت‌نشده می‌ماندند، یعنی دقیقاً همان اشتباهی که این
اسکریپت برای جلوگیری از آن نوشته شده.

قاعده: **اگر ردیف لاگ هست، همان برنده است** (عددی که پنل اودو نشان می‌داده و
کارمند بر اساسش عمل کرده)؛ وگرنه مانده = سهم میزبان منهای مجموع پرداخت‌ها.
۵۹۷ رزرو که هیچ سابقه‌ای ندارند **دست نمی‌خورند** — «سابقه‌ای نیست» با «پرداخت
نشده» یکی نیست.

**کیف پول‌ها دست نمی‌خورند.** این پرداخت‌ها هرگز از کیف پول این سیستم خارج
نشده‌اند و نوشتنشان در آن، موجودی جعلی می‌ساخت.

## دسترسی

فعلاً فقط `role = ADMIN`. اندپوینت `permission` برای هر کاربر لاگین‌شده جواب
می‌دهد (نه ۴۰۳)، چون صفحه باید بتواند «دسترسی ندارید» نشان دهد نه یک خطای مبهم.

## تست روی سرور

| | |
|---|---|
| فهرست | ۱۰ رزرو مرداد ۱۴۰۵ با سهم، مانده و اطلاعات بانکی واقعی |
| ثبت بیعانه ۴۰۰٬۰۰۰ | `kind: DEPOSIT` ✓ |
| واریز بیشتر از مانده | رد شد: «مانده واریز این رزرو ۶۰۰٬۰۰۰ تومان است» ✓ |
| ویرایش مانده به ۵۰۰٬۰۰۰ | `remainder_update` با مقدار **−۱۰۰٬۰۰۰** ✓ |
| تسویه گروهی ۳۰۰٬۰۰۰ | `{settled: 1, unallocated: 0}` ✓ |
| کارت ۳ رقمی | رد شد ✓ · شبای درست ذخیره شد ✓ |
| توضیحات تیم فروش | ذخیره و در ردیف نمایش داده شد ✓ |

و خود صفحه در مرورگر یک ردیف واقعی رندر کرد: میزبان، کد رزرو، تاریخ قطعی جلالی،
سهم ۳٬۱۷۳٬۰۰۰، بیعانه، مانده، تگ وضعیت و جمع ستون‌ها.

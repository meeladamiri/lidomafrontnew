## این پروژه دقیقاً چیه؟

**لیدوماتریپ قبلاً روی Odoo اجرا می‌شد** — بک‌اند production واقعی (`lidomatrip.com`) هنوز روی Odoo زنده‌ست و فرانت‌اند قدیمی (همون کدبیس Next.js که الان داریم روش کار می‌کنیم) باهاش از طریق پروتکل JSON-RPC اودو حرف می‌زد.

**هدف این پروژه: مهاجرت کامل از Odoo به یه بک‌اند جدید و مستقل** (Express + TypeScript + Prisma + PostgreSQL) — یعنی:

1. یه بک‌اند کاملاً جدید از صفر نوشته شد (`backend/`) که هیچ وابستگی‌ای به Odoo نداره — همون کارکردهای Odoo (کاربر، اقامتگاه، رزرو، پرداخت و...) رو با REST API و دیتابیس PostgreSQL خودش پیاده‌سازی می‌کنه.
2. **فرانت‌اند قدیمی (همون کدی که قبلاً به Odoo وصل بود) دور ریخته یا بازنویسی نشد** — به‌جاش، فقط لایه‌ی ارتباطی‌ش (`api/*.ts`) یکی‌یکی از پروتکل JSON-RPC اودو به REST جدید سوییچ داده شد. کامپوننت‌های UI دست‌نخورده موندن.
3. یعنی الان: همون سایتی که کاربر می‌بینه (همون UI، همون آدرس‌ها)، پشت صحنه دیگه به Odoo وصل نیست — به بک‌اند اکسپرس جدید وصله. این کار برای مسیرهای اصلی (auth، جستجو، مشاهده، رزرو، ویزارد ثبت اقامتگاه، ویرایش اقامتگاه، پنل ادمین، آپلود فایل) **کامل انجام شده و تست شده**.

چیزی که **هنوز باقی مونده و این مهاجرت رو ۱۰۰٪ نمی‌کنه**: خودِ **داده‌های واقعی** (کاربران واقعی، اقامتگاه‌های واقعی، رزروهای واقعی) که الان توی دیتابیس Odoo قدیم هستن، هنوز به دیتابیس PostgreSQL جدید منتقل نشدن — دیتابیس جدید فقط داده‌ی seed/تستی داره. این آیتم شماره‌ی ۱ توی لیست «چی هنوز مونده» پایین همینه.

**نکته‌ی حیاتی:** همه‌ی این‌ها **سورس‌کد** Odoo هستن (مدل داده، منطق، فرانت قدیمی خودِ Odoo)، نه **دیتای واقعی** (کاربرها، اقامتگاه‌های واقعی، رزروهای واقعی). روی این لپ‌تاپ هیچ فایل dump دیتابیس (`.sql`/`.dump`/`.backup`) پیدا نکردم — فقط کانفیگ. یعنی برای مهاجرت **داده‌ی واقعی** (نه فقط ساختار)، احتمالاً باید یا:
- به سرور production زنده (`lidomatrip.com`، که هنوز روشنه) دسترسی مستقیم دیتابیس گرفت، یا
- یه dump تازه از همون سرور تهیه کرد.

این دقیقاً همون چیزیه که قبلاً پرسیده بودم و منتظر تصمیم شما موند («مهاجرت داده‌ی واقعی از Odoo قدیم»، آیتم ۱ توی لیست پایین) — حالا با این اطلاعات دقیق‌تر، اگه دسترسی دیتابیس/سرور production رو بدید، می‌تونم با کمک همین سورس‌های Odoo (که الان می‌دونم مدل‌های دقیقش کجاست) یه اسکریپت migration واقعی بنویسم.

### دقیقاً قراره چیکار کنیم (خلاصه‌ی پلن، ۲ فاز)

**هدف نهایی: سئوی قوی.** دلیل اصلی این مهاجرت اینه که فرانت‌اند مهمان (خصوصاً صفحه‌ی اصلی، صفحات جستجو/فیلتر، و صفحه‌ی هر اقامتگاه) در نهایت باید کاملاً سئو-محور باشه — یعنی هرجا که برای سئو مهمه، رندر باید **سمت سرور (SSR)** باشه، نه کلاینت‌ساید. ولی این کار توی **فاز دوم** انجام می‌شه، نه الان.

**فاز ۱ (همینی که تا الان انجام دادیم، تقریباً تمومه):** اول بک‌اند جدید لیدوما رو حرفه‌ای‌تر، درست‌تر و کامل‌تر بالا آوردیم (Express+Prisma بجای Odoo)، و یه پنل ادمین راحت‌تر و بهتر برای کارمندها ساختیم که بتونن راحت کاراشون (رزرو، کاربر، اقامتگاه) رو انجام بدن. فرانت‌اند مهمان فعلاً فقط از نظر **عملکردی** به بک‌اند جدید وصل شد (کار کنه، داده‌ی درست نشون بده) — هنوز از نظر سئو بازبینی/بهینه نشده.

**فاز ۲ (بعدی، هنوز شروع نشده):** وقتی نسخه‌ی فاز ۱ حرفه‌ای و پایدار شد، برمی‌گردیم سراغ فرانت‌اند و مشکلاتش رو برطرف می‌کنیم تا بهترین سئوی ممکن رو داشته باشه — مثلاً مطمئن بشیم صفحه‌ی اصلی، صفحات جستجو، و صفحات اقامتگاه هرجا مهمه سمت سرور رندر می‌شن، نه کلاینت‌ساید.

**خبر خوب:** پایه‌ی این کار از قبل تا حدی وجود داره — سه صفحه‌ی کلیدی همین الان هم رندرشون سمت سرور/build-time‌ه، نه کلاینت‌ساید خالص:
- صفحه‌ی اصلی (`pages/index.tsx`): `getStaticProps` + بازتولید هر ۳۰ دقیقه (ISR)
- صفحات جستجو (`pages/search/index.tsx`, `pages/search/[id].tsx`): `getServerSideProps`
- صفحه‌ی اقامتگاه (`pages/rentals/[id].tsx`): `getServerSideProps`

ولی این‌ها فقط برای **درست کار کردن** (نه رفتن مستقیم به production قدیمی) تنظیم شدن، نه با یه بازبینی مخصوص سئو (متادیتا، structured data، سرعت، و...). فاز ۲ دقیقاً یعنی این بازبینی رو انجام بدیم.

## تصمیمات معماری کلیدی (باید رعایت بشه)

1. **Reshape در لایه‌ی API، نه دست‌کاری کامپوننت‌ها.** هیچ‌کدوم از کامپوننت‌های UI فرانت (حتی ویزارد ۴۲ فایلی ثبت اقامتگاه) دست‌خورده نشدن. هر فایل `api/*.ts` پاسخ REST جدید رو می‌گیره و دقیقاً به شکل envelope قدیمی (`{status, params:{...}}`) reshape می‌کنه.
2. **فیلدهای غایب همیشه default امن** (`[]`، نه `undefined`) — چون کد قدیمی جاهایی بدون optional chaining `.map()`/`.filter()` می‌زنه.
3. **قابلیت‌هایی که بک‌اند معادل نداره** (رزرو اتاق بوم‌گردی، ویرایش رزرو، کد تخفیف): `Promise<any>` که `{status:"error", err_msg:"..."}` برمی‌گردونه — نه crash، نه silent fail.
4. **بعد از هر تغییر: `npx tsc --noEmit` توی هر دو پروژه باید صفر خطا بده.** این تنها verification قابل‌اتکاست چون تست مرورگر غیرقابل‌اعتماده.
5. **قبل از commit به `front`**: چک کن `yarn.lock` توسط `npm install` خراب نشده (این سیستم yarn نصب نداره؛ برای نصب پکیج از `npx yarn@1.22.19 add ...` استفاده کن، نه `npm install`، وگرنه لاک‌فایل به‌هم می‌ریزه).
6. Object storage (`middleware/upload.ts`): اگه env vars ی Liara ست نباشن، خودکار می‌ره سراغ دیسک محلی — همون الگوی «بدون کانفیگ گریسفول دیگرید کن» که برای SMS provider هم استفاده شده.

## چی هنوز مونده (اولویت‌بندی‌شده)

### فاز ۱ — تکمیل بک‌اند/ادمین (اولویت فعلی)

1. **مهاجرت داده‌ی واقعی از Odoo قدیم** — بزرگ‌ترین آیتم. متوقف مونده، منتظر تصمیم شما درباره‌ی نحوه‌ی دسترسی به دیتابیس/API اودو (جزئیات کامل بالا، بخش «منابع»).
2. **سرویس پیامکی واقعی** — کلید API نداریم، فقط کد OTP رو لاگ می‌کنه.
3. **پروفایل کامل کاربر** — ویرایش اطلاعات، آپلود آواتار.
4. **بنر/محتوای CMS صفحه‌ی اصلی و فوتر** — نه مدل دیتابیس داره نه پنل مدیریت (زیرساخت آپلودش الان آماده‌ست، فقط قابلیت نیست).
5. **نقش «کارشناس» جدا از ادمین کامل** — فعلاً فقط دو نقش `USER`/`ADMIN` هست.
6. **صفحه‌ی جزئیات رزرو/کاربر توی پنل ادمین** — فعلاً فقط لیسته.
7. **بوم‌گردی سطح-اتاق** (رزرو/قیمت‌گذاری per-room) — نیاز به تغییر معماری فرانت (الان با پیام خطای تمیز مسدوده، نه crash).
8. **نظرات و امتیازها** — اصلاً مدل نشده (Phase 2 بک‌اند).
9. **کیف پول، تسویه میزبان، چت رزرو، شکایات، ووچر** — Phase 2 بک‌اند، هیچ‌کدوم ساخته نشده.
10. **صفحه‌ی عمومی پروفایل میزبان** — دست‌نخورده.
11. **درگاه پرداخت** — هنوز بررسی نشده وصله یا نه.
12. **دیپلوی روی سرور واقعی** — فعلاً فقط dev محلی.

### فاز ۲ — سئوی فرانت‌اند مهمان (بعد از تکمیل فاز ۱)

13. **بازبینی سئوی صفحه‌ی اصلی، جستجو، و اقامتگاه** — این‌ها الان SSR/ISR هستن ولی فقط برای درست‌کارکردن تنظیم شدن، نه با هدف سئو (متادیتا، structured data، سرعت لود، Core Web Vitals و...).
14. **بررسی بقیه‌ی صفحاتی که هنوز کلاینت‌ساید (CSR) هستن** و تصمیم بگیریم کدوم‌ها برای سئو مهمن و باید SSR بشن.

آخرین کار: زیرساخت آپلود فایل از دیسک محلی به Liara Object Storage سوییچ شد (bucket: `lidoma-uploads`)، تست کامل شد، commit و push شد (هر دو ریپو تمیزن، چیزی pending نیست).

اگه بخوایم ادامه بدیم، ترتیب طبیعی همون لیست بالاست — آیتم ۱ (مهاجرت داده) بزرگ‌ترینه و نیاز به تصمیم شما داره؛ بقیه رو می‌شه مستقل و به‌ترتیب دلخواه جلو برد.

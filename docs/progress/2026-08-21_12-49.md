## این پروژه دقیقاً چیه؟

**لیدوماتریپ قبلاً روی Odoo اجرا می‌شد** — بک‌اند production واقعی (`lidomatrip.com`) هنوز روی Odoo زنده‌ست و فرانت‌اند قدیمی (همون کدبیس Next.js که الان داریم روش کار می‌کنیم) باهاش از طریق پروتکل JSON-RPC اودو حرف می‌زد.

**هدف این پروژه: مهاجرت کامل از Odoo به یه بک‌اند جدید و مستقل** (Express + TypeScript + Prisma + PostgreSQL):

1. یه بک‌اند کاملاً جدید از صفر نوشته شد (`backend/`) که هیچ وابستگی‌ای به Odoo نداره.
2. فرانت‌اند قدیمی دور ریخته یا بازنویسی نشد — فقط لایه‌ی ارتباطی‌ش (`api/*.ts`) یکی‌یکی از JSON-RPC اودو به REST جدید سوییچ داده شد. کامپوننت‌های UI دست‌نخورده موندن.
3. **مرحله‌ی «کارکردی» تمومه:** همون سایتی که کاربر می‌بینه دیگه به Odoo وصل نیست.
4. **مرحله‌ی «دیتای واقعی» هم امروز تمام شد برای کاربرها و عکس‌ها** (جزئیات کامل پایین‌تر) — این بزرگ‌ترین آیتم باز قبلی بود.

- ابزارهای نصب‌شده روی این سرور: `node` (v16.19.1 — قدیمیه، برای AWS SDK v3 باید با فلگ `--experimental-global-webcrypto` اجرا بشه)، `npm`، `python3` (بدون boto3)، `rclone` (کار نکرد، ناسازگاری عجیب با S3 گیت‌وی Liara — access denied روی PUT حتی با credential درست؛ به‌جاش از `@aws-sdk/client-s3` مستقیم استفاده شد).

### دیتابیس مقصد و restore کامل Odoo

- دیتابیس اصلی جدید: همون Liara Postgres که بک‌اند استفاده می‌کنه (`DATABASE_URL` توی `.env`، دیتابیس `postgres`، schema `public`).
- **کل دامپ Odoo روی همون سرور Liara، توی یه دیتابیس کاملاً جدا به اسم `odoo_legacy` restore شده** (نه schema جدا، دیتابیس جدا — چون Postgres query بین دیتابیس نمی‌ذاره، اسکریپت‌های migration دو تا PrismaClient جدا می‌سازن: یکی برای خوندن از `odoo_legacy` با `$queryRawUnsafe`، یکی برای نوشتن توی schema اصلی). نتیجه: ۱۵ گیگ، ۵۵۵ جدول، شامل ۳۱۳,۴۵۳ ردیف `res_partner` و ۳۴۸,۰۷۲ ردیف `sale_order`.
- پلن Liara Postgres آپگرید شد به **«زحل»** (۴ گیگ رم) با دیسک ۴۰-۵۰ گیگ (برای جا شدن دیتای مهاجرت‌شده).
- `DATABASE_URL` یه `connection_limit=20` هم گرفت (پیش‌فرض Prisma فقط ۵ بود و باعث pool timeout زیر بار migration می‌شد).

### تصمیمات کلیدی مهاجرت (باید توی migration های بعدی هم رعایت بشه)

1. **رمز عبور کاربرهای migrate‌شده منتقل نمی‌شه.** الگوریتم هش Odoo (احتمالاً pbkdf2 از طریق passlib) با bcrypt بک‌اند جدید سازگار نیست. کاربرهای قدیمی با OTP لاگین می‌کنن، هر وقت خواستن رمز جدید می‌سازن.
2. **دیدوپ بر اساس شماره تلفن نرمال‌شده** (فرمت `09xxxxxxxxx`؛ کد کشور/فاصله/خط‌تیره حذف می‌شه). وقتی چند ردیف Odoo به یه شماره می‌رسن، اونی که `res_users` (لاگین واقعی) داره یا `write_date` جدیدتره برنده می‌شه.
3. **hostId توی migration اقامتگاه‌ها از طریق شماره‌تلفنِ میزبانِ Odoo resolve می‌شه** به کاربرِ از قبل migrate‌شده — یعنی migration کاربران همیشه باید *قبل* از اقامتگاه‌ها کامل تموم بشه.
4. **عکس‌ها:** فقط URL (متن) توی دیتابیس ذخیره می‌شه، هیچ باینری‌ای توی Postgres نیست. آپلود مستقیماً از سرور مبدأ به همون باکت Liara Object Storage (`lidoma-uploads`) که بک‌اند از قبل استفاده می‌کنه — کلید آبجکت‌ها زیر پیشوند `migrated/`.
5. **کاتالوگ‌های خالی (شهر، امکانات، قوانین) رد شدن** — چون taxonomy تمیزی برای match‌کردن باهاشون هنوز طراحی نشده. این آیتم‌های داده برای این residence ها فعلاً `null`/خالی می‌مونن.
6. اسکریپت‌های migration همیشه یه حالت **dry-run پیش‌فرض** دارن (فقط با `--commit` واقعاً می‌نویسن) و **idempotent** هستن (چک existence قبل از create).
7. **Concurrency باید با `connection_limit` هماهنگ باشه** — یه بار با concurrency=25 در مقابل pool=5 اجرا شد و کلی pool-timeout error داد؛ درس گرفته‌شده: همیشه concurrency رو چند واحد کمتر از connection_limit نگه دار.

### ⚠️ نکته‌ی Prisma generate روی Windows (وقتی سرور dev یا اسکریپتی در حال اجراست)

اگه schema.prisma عوض بشه و بخوایید `npx prisma generate` بزنید، ولی سرور dev بک‌اند یا یه اسکریپت migration در حال اجرا باشه، روی Windows با خطای `EPERM: operation not permitted, unlink ...query_engine-windows.dll.node` fail می‌شه (فایل باینری توسط پردازش زنده قفل شده).

**راه‌حل بدون نیاز به کشتن پردازش زنده:**

```bash
# 1. یه کپی از schema با output متفاوت بساز
sed 's#output   = "../src/generated/prisma/client"#output   = "../src/generated/prisma-tmp/client"#' prisma/schema.prisma > prisma/schema-tmp.prisma

# 2. generate به مسیر موقت (قفل نیست)
npx prisma generate --schema=./prisma/schema-tmp.prisma

# 3. فقط فایل‌های JS/TS رو کپی کن — نه باینری .dll.node (که schema-specific نیست، نیازی به تعویض نداره)
cp src/generated/prisma-tmp/client/index.js src/generated/prisma/client/index.js
cp src/generated/prisma-tmp/client/index.d.ts src/generated/prisma/client/index.d.ts
cp src/generated/prisma-tmp/client/schema.prisma src/generated/prisma/client/schema.prisma
cp src/generated/prisma-tmp/client/default.js src/generated/prisma/client/default.js
cp src/generated/prisma-tmp/client/default.d.ts src/generated/prisma/client/default.d.ts

# 4. پاکسازی
rm -rf src/generated/prisma-tmp prisma/schema-tmp.prisma
```

## تصمیمات معماری کلیدی (باید رعایت بشه)

1. **Reshape در لایه‌ی API، نه دست‌کاری کامپوننت‌ها.** هر فایل `api/*.ts` پاسخ REST جدید رو دقیقاً به شکل envelope قدیمی (`{status, params:{...}}`) reshape می‌کنه. وقتی تایپ دقیق‌تر باعث خطای تایپ توی یه کامپوننت قدیمی می‌شه (چون قبلاً `any` بود)، فقط یه type cast تک‌خطی اضافه کن، نه تغییر منطق.
2. **فیلدهای غایب همیشه default امن** (`[]`، نه `undefined`).
3. **قابلیت‌هایی که بک‌اند معادل نداره:** `Promise<any>` که `{status:"error", err_msg:"..."}` برمی‌گردونه.
4. **بعد از هر تغییر: `npx tsc --noEmit` توی هر دو پروژه باید صفر خطا بده.**
5. **قبل از commit به `front`**: چک کن `yarn.lock` خراب نشده (این سیستم yarn نصب نداره؛ `npx yarn@1.22.19 add ...`، نه `npm install`).
6. Object storage: بدون کانفیگ گریسفول دیگرید به دیسک محلی می‌کنه.
7. **برای endpoint های ادمین که معادل «سمت میزبان/مهمان» دارن**، اول چک کن میشه با resolve کردن hostId/ownership واقعی، همون سرویس موجود رو صدا زد (به‌جای کپی منطق) — دقیقاً همین الگو برای اقامتگاه و رزرو استفاده شد.
8. **صفحات جدید پنل ادمین: Tailwind.** صفحات قدیمی (`admin.css`) به‌مرور و در فرصت مناسب بازنویسی می‌شن، نه یکجا.

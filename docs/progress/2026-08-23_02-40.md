### دستورهای اجراشده (به ترتیب، هرکدوم idempotent، توی `backend/`)

```bash
npx tsx scripts/migrate-odoo-users.ts --commit
npx tsx scripts/migrate-odoo-residences.ts --commit   # قبلش scripts/upload-images.js باید رو سرور مبدأ اجرا بشه، بعد image-map.json دانلود بشه
npx tsx scripts/migrate-odoo-cities.ts --commit         # استان/شهر + backfill cityId
npx tsx scripts/migrate-odoo-reservations.ts --commit
npx tsx scripts/backfill-odoo-latlng.ts --commit
npx tsx --env-file=.env scripts/fix-city-slugs-from-odoo.ts --commit   # اسلاگ واقعی x_title_en — جایگزین backfill-city-slugs.ts (بازنشسته: ترنسلیتره‌هاش غلط بودن، مثلاً یزد→izd)
npx tsx --env-file=.env scripts/migrate-odoo-tag-urls.ts --commit       # tag_url اودو → legacy_redirects (۹,۸۹۰ مسیر /tags/... با هدف 301)
npx tsx scripts/migrate-odoo-calendar.ts --commit
# روی سرور مبدأ (SSH):
node --experimental-global-webcrypto upload-host-avatars.js   # بعدش host-avatar-map.json دانلود بشه
npx tsx scripts/backfill-host-avatars.ts --commit
```

**نکته‌ی تکرارپذیری مهم:** همه‌ی این اسکریپت‌ها idempotent هستن (چک existence قبل از نوشتن) — اگه هرکدوم وسط راه با خطای connection موقت (خیلی زیاد پیش اومد، چون Liara زیر بار migration سنگین کند می‌شه) fail بشه، فقط دوباره همون دستور رو بزن، از همونجا ادامه می‌ده.

### چیزی که هنوز باز مونده در مهاجرت دیتا

فقط **کاتالوگ امکانات/قوانین** (از `x_rooms_features` Odoo) باقی مونده — چون کاتالوگ هدف (`amenities`/`rules`) هنوز تقریباً خالیه و نیاز به طراحی یه taxonomy تمیز داره، نه صرفاً کپی مکانیکی.

### تصمیمات کلیدی مهاجرت

1. **رمز عبور منتقل نمی‌شه** (هش Odoo با bcrypt جدید ناسازگاره) — کاربرهای قدیمی با OTP لاگین می‌کنن.
2. **دیدوپ کاربران بر اساس شماره‌تلفن نرمال‌شده**؛ رکورد دارای `res_users` یا `write_date` جدیدتر برنده می‌شه.
3. **hostId/guestId/residenceId همیشه از طریق resolve کردن phone→user یا `reference="ODOO-<id>"`→residence پیدا می‌شن** — یعنی ترتیب اجرا مهمه: کاربران قبل از اقامتگاه‌ها، اقامتگاه‌ها قبل از رزروها/تقویم.
4. **فقط دیتای واقعی و فعلاً مرتبط migrate می‌شه**، نه هرچی هست: فقط اقامتگاه‌های منتشرشده، فقط رزروهای واقعاً تأییدشده (`state=sale`)، فقط تاریخ‌های تقویمِ آینده، فقط آواتارهای واقعی (نه پیش‌فرض). این‌ها همه تصمیم آگاهانه بودن برای جلوگیری از شلوغی بی‌فایده، نه محدودیت فنی.
5. **عکس‌ها فقط URL (نه باینری) توی دیتابیس** — آپلود مستقیم از سرور مبدأ به باکت Liara (`lidoma-uploads`) با کلید `migrated/...`.
6. اسکریپت‌ها همیشه dry-run پیش‌فرض (`--commit` برای نوشتن واقعی) و idempotent.
7. **Concurrency باید با `connection_limit` هماهنگ باشه** (درس گرفته‌شده از یه تجربه‌ی بد اولیه با pool timeout).
8. **موقع نوشتن exists-check با یه فیلد nullable توی compound unique key** (مثل `CalendarDay`'s `roomId`)، از `findFirst` استفاده کن نه `findUnique` — Prisma با `null` توی `findUnique` روی compound key خطا می‌ده حتی اگه ستون nullable باشه.
9. **PostgreSQL auto-increment sequence با seed data دستی هماهنگ نیست به‌صورت پیش‌فرض** — اگه یه جدول از قبل چندتا ردیف seed با id دستی داشته باشه، اولین `create()` بعدی ممکنه به unique constraint بخوره. رفعش: `SELECT setval('<table>_id_seq', (SELECT MAX(id) FROM <table>));`

### ⚠️ نکته‌ی Prisma generate روی Windows (وقتی سرور dev یا اسکریپتی در حال اجراست)

اگه schema.prisma عوض بشه ولی یه پردازش (سرور dev یا اسکریپت migration) در حال اجرا باشه، `npx prisma generate` با `EPERM: operation not permitted, unlink ...query_engine-windows.dll.node` fail می‌شه. راه‌حل بدون کشتن پردازش زنده:

```bash
sed 's#output   = "../src/generated/prisma/client"#output   = "../src/generated/prisma-tmp/client"#' prisma/schema.prisma > prisma/schema-tmp.prisma
npx prisma generate --schema=./prisma/schema-tmp.prisma
cp src/generated/prisma-tmp/client/{index.js,index.d.ts,schema.prisma,default.js,default.d.ts} src/generated/prisma/client/
rm -rf src/generated/prisma-tmp prisma/schema-tmp.prisma
```
(باینری `.dll.node` عمداً کپی نمی‌شه — schema-specific نیست، نیازی به تعویض نداره.)

### نشست‌های اخیر (به‌ترتیب)

- **پنل ادمین:** جزئیات کاربر (+ رفع نشتی امنیتی `passwordHash`)، جزئیات رزرو (نمایش کامل + ۳ اکشن: `forceApprove`/`markDone`/`cancel`)، جزئیات اقامتگاه (۶ تب کاملاً قابل‌ویرایش، با استفاده‌ی مجدد از سرویس‌های سمت میزبان)، لیست اقامتگاه‌ها (toggle کارتی/ردیفی + فیلتر سفارشی + پریست ذخیره‌شده در دیتابیس).

## تصمیمات معماری کلیدی (باید رعایت بشه)

1. **Reshape در لایه‌ی API، نه دست‌کاری کامپوننت‌ها.** وقتی تایپ دقیق‌تر باعث خطای تایپ توی کامپوننت قدیمی می‌شه، فقط type cast تک‌خطی اضافه کن.
2. **فیلدهای غایب همیشه default امن** (`[]`، نه `undefined`).
3. **قابلیت بدون معادل بک‌اند:** `Promise<any>` که `{status:"error", err_msg:"..."}` برمی‌گردونه.
4. **بعد از هر تغییر: `npx tsc --noEmit` توی هر دو پروژه صفر خطا.**
5. **قبل از commit به `front`:** `yarn.lock` رو با `npx yarn@1.22.19 add ...` دست بزن، نه `npm install`.
6. **endpoint های ادمین معادل سمت میزبان/مهمان:** به‌جای کپی منطق، hostId/ownership واقعی رو resolve کن و همون سرویس موجود رو صدا بزن.
7. **صفحات جدید پنل ادمین: Tailwind.** قدیمی‌ها تدریجی بازنویسی می‌شن.
8. **next.config.js عوض شد؟ سرور dev رو کامل ری‌استارت کن** — Next.js تغییرات این فایل رو hot-reload نمی‌کنه.

## سیستم URL های قدیمی و سئو (نشست 2026-08-23)

سایت قدیم هزاران URL ایندکس‌شده داره که نباید سئوشون آسیب ببینه. ساختار قدیم و معادل جدید:

| URL قدیمی | رفتار |
|---|---|
| `/search/<slug>` (مثل `/search/tehran`) | صفحه‌ی اصلی شهر — اسلاگ‌ها دست‌ساز تیم توی پنل اودو (`product_public_category.x_title_en`)، **نه ترنسلیتره**. بک‌اند الان `cityName` رو روی `City.titleEn`/`name` و `Province.titleEn`/`name` مچ می‌کنه. |
| `/tags/<tag>/<اسلاگ-فارسی>` | ~۱۰ هزار صفحه‌ی سئویی تگ×شهر → **301** به `/search/<city>?<tag>=1` (مثل پروداکشن). نگاشت‌ها از جدول `tag_url` اودو به `legacy_redirects` مهاجرت شدن؛ endpoint: `GET /api/search/legacy-redirect?path=...`؛ صفحه‌ی catch-all: `front/pages/tags/[...slug].tsx`. اسلاگ ناشناس → `/search`. |
| `/search/city/<نام-فارسی>-<id>` | فرمت خیلی قدیمی → **301** به `/search/<slug>` — `front/pages/search/city/[id].tsx`. |
| `/search/shomal` | «region» اودو (بدون شهر/استان مشخص) — alias توی بک‌اند: شمال = مازندران+گیلان+گلستان. بقیه‌ی region ها (westtehran و…) هنوز پیاده نشدن. |

- تگ‌های دسته‌بندی الان **اتربیوت** روی همون صفحه‌ی لیست هستن (`?villa=1`) — کلیدها همون `website_tags.x_title` اودو (villa/pool/jacuzzi/hotelapartment/...). فقط `boomgardi` الان واقعاً فیلتر می‌کنه (→ `type=BOOMGARDI`)؛ بقیه منتظر مهاجرت کاتالوگ امکاناتن.
- کارت‌های دسته‌بندی صفحه‌ی اصلی (دسکتاپ+موبایل) به فرمت جدید لینک شدن؛ لینک‌های `BASE_URL` (دامنه‌ی قدیم) توی بنرها/مقصدهای‌محبوب نسبی شدن؛ دو اسلاگ هاردکد غلط (esfahan→isfahan، foman→fuman) اصلاح شدن.
- ریدایرکت‌ها با `statusCode: 301` صریح (نه 308ِ `permanent: true`) برای هم‌ارزی با پروداکشن.

## دقیقاً کجا متوقف شدیم

مهاجرت کامل دیتای واقعی (کاربران، عکس‌ها، اقامتگاه‌ها، اتاق‌ها، شهر/استان، رزروها، مختصات، آواتار میزبان، تقویم) تموم شد. ۸ باگ صفحات اقامتگاه (تست دستی کاربر) رفع شدن. **نشست 2026-08-23:** سیستم اسلاگ/سئو کامل شد (جدول بالا) — اسلاگ‌های واقعی جایگزین ترنسلیتره شدن، ۹,۸۹۰ ریدایرکت 301 برای `/tags/...` زنده شد، کارت‌های ۴۰۴ صفحه‌ی اصلی درست شدن، و فیلتر بوم‌گردی واقعی شد (تست: `/search/isfahan?boomgardi=1` → ۱۴۲ از ۴۶۱).

**قدم بعدی طبیعی:** کاتالوگ امکانات/قوانین (آیتم ۱ لیست بالا) — الان دو دلیل داره: هم فرم ثبت/ویرایش اقامتگاه بهش نیاز داره، هم تگ‌های سئویی (`?villa=1` و ۱۲ تای دیگه) تا نباشه فیلتر نمی‌کنن. نقشه‌ی feature-id ها توی `website_tags.x_domain` آماده‌ست.

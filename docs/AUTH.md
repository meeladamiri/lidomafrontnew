# احراز هویت، نقش و ریدایرکت

`middleware.ts` · `utilities/auth/{redirect,claims}.ts` · `providers/Profile.tsx` ·
`components/Auth/*` · `utilities/{cookies,doLogoutActions}.ts` · `api/index.tsx`

## وضعیتی که از آن شروع کردیم

سه چیز هم‌زمان غلط بود، و هر سه از یک جنس: تصمیم‌ها دیر گرفته می‌شدند و در
چند جا تکرار شده بودند.

**۱. هیچ‌چیز از مسیرهای پنل محافظت نمی‌کرد.** هر گارد `getServerSideProps` در
پروژه **کامنت شده** بود (`dashboard`، `wallet`، `residences/list`،
`b-room/[id]/edit`) و middleware هم وجود نداشت. بازکردن `/dashboard` در حالت
خروج یعنی کل پوسته رندر می‌شد، درخواست‌هایش ۴۰۱ می‌گرفتند، و کاربر توی پنلی
می‌ماند که کار نمی‌کرد.

**۲. نقش با دو درخواست پشت‌سرهم فهمیده می‌شد.** `checkUserStatus` باید تمام
می‌شد تا `getAccountInfo` **اجازه‌ی شروع** بگیرد، و تا وقتی اولی نیامده بود
`is_host` مقدار `false` داشت. یعنی هدر، منوی کناری و نوار پایین اول نسخه‌ی
مهمان را می‌کشیدند و بعد زیر دست کاربر جابه‌جا می‌شدند — همان چیزی که
«انگار وارد یک پنل شدم و بعد ریدایرکت شدم» توصیفش می‌کند، در حالی که اصلاً
ریدایرکتی در کار نبود.

**۳. تصمیم مقصدِ بعد از ورود، چهار نسخه‌ی ناسازگار داشت.** `OTP`،
`EnterPassword`، `SignupForm` و `ForgetPassword` هرکدام جدا تصمیم می‌گرفتند و
از هم دور افتاده بودند: دوتا میزبان را به `/dashboard` و مهمان را به صفحه‌ی
اصلی می‌فرستادند، یکی همه را به صفحه‌ی اصلی. یعنی مقصدِ ورود به این بستگی
داشت که از کدام در وارد شده‌ای.

## تصمیم معماری: تصمیم قبل از رندر، در یک جا

پروژه pages router است و توکن در **کوکی** (`session_id`) می‌نشیند — یعنی سرور
هم می‌تواند ببیندش. پس تصمیم به middleware منتقل شد:

```
درخواست → middleware می‌بیند کوکی هست یا نه → یا رندر، یا ۳۰۷ به ورود
```

نه فلشِ پنلی که نمی‌شود استفاده کرد، نه از دست رفتن آدرسِ مقصد، و یک قانون در
یک فایل به‌جای گاردی در هر صفحه که فراموش شود (همان‌طور که هر چهارتا شده بود).

### چرا فقط احراز هویت، نه نقش

middleware عمداً **نقش را گیت نمی‌کند**. API هر کوئری میزبان را با id خودِ
کاربر محدود می‌کند، پس مهمانی که به مسیر میزبان برسد فهرست خالی می‌بیند نه
داده‌ی کس دیگر — تجربه‌ی بد است، نه نشتی. و اگر فهرست مسیرها یک بار غلط
نوشته شود، ریدایرکتِ نقش‌محور آدم‌ها را از صفحه‌ی خودشان بیرون می‌اندازد.
پس نقش در **ناوبری** مدیریت می‌شود: چیزی که نباید ببینی، لینکش را نمی‌گیری.

نمونه‌ی عملی: مهمان روی `/residences/list` جواب ۲۰۰ می‌گیرد و یک empty state
درست می‌بیند («هنوز اقامتگاهی ثبت نکردی» + دکمه‌ی شروع ثبت) — که بهتر از
ریدایرکت است.

### توکن منقضی ≠ نشست مرده

`refresh_token` سی روز عمر دارد و کلاینت روی اولین ۴۰۱ عوضش می‌کند. اگر
middleware هر توکن منقضی را به ورود می‌فرستاد، هر دو هفته همه را بی‌دلیل
بیرون می‌انداخت. پس: توکن منقضی **با** refresh رد می‌شود، **بدون** refresh
به ورود می‌رود.

## نقش، از روی کوکی و قبل از اولین نقاشی

JWT داخل کوکی هر دو چیز لازم را دارد (`sub` و `isHost`). `readTokenClaims()`
آن را می‌خواند — بدون درخواست، همگام.

یک تله‌ی مهم: این **نمی‌تواند مقدار اولیه‌ی state باشد**. سرور موقع رندر کوکی
در دست ندارد، پس اولین رندر کلاینت با سرور اختلاف پیدا می‌کند و React کل
مارک‌آپ را دور می‌ریزد (hydration mismatch — تلاش اول همین را ساخت). راه درست
`useIsomorphicLayoutEffect` است: بعد از تطبیق hydration، قبل از paint. پس
نسخه‌ی مهمان هیچ‌وقت واقعاً دیده نمی‌شود.

`getAccountInfo` هم دیگر پشت `checkUserStatus` صف نمی‌ایستد؛ هر دو با وجود
توکن هم‌زمان می‌روند. اندازه‌گیری روی یک بارگذاری تمیز: `/api/auth/me` و
`/api/users/me` موازی، مجموع پنج درخواست بدون تکرار.

> امضای توکن **بررسی نمی‌شود** و لازم هم نیست: این تصمیم می‌گیرد کدام صفحه
> رندر شود، نه چه داده‌ای تحویل کسی برود. API هر درخواست را خودش تأیید می‌کند.

## مقصد بعد از ورود — یک نقطه

`utilities/auth/redirect.ts`:

| ورودی | مقصد |
|---|---|
| `redirectTo` معتبر | همان مسیر |
| بدون `redirectTo` | `/dashboard` (برای میزبان و مهمان) |
| ورود از داخل مودال | هیچ ناوبری‌ای — فقط بستن مودال |

دو قاعده پشتش:

- **اگر جایی می‌رفتند، ببرشان همان‌جا.** هر چیز دیگری دلیل ورودشان را دور
  می‌ریزد.
- **وگرنه پنل، برای همه.** `/dashboard` مهمان را هم سرو می‌کند و خود پنل با
  نقش تطبیق پیدا می‌کند، پس اینجا چیزی برای شاخه‌زدن روی نقش نمانده.

ورود از مودال عمداً اصلاً ناوبری نیست: کسی که وسط انتخاب تاریخ روی یک
اقامتگاه وارد می‌شود باید همان‌جا بماند. کد قبلی میزبان‌ها را جابه‌جا می‌کرد
و مهمان‌ها را سرجایشان می‌گذاشت.

## Open redirect — یک آسیب‌پذیری واقعی که بسته شد

`redirectTo` مستقیم از query می‌آمد و بی‌بررسی به `router.push` می‌رفت. یعنی
`?redirectTo=https://evil.example` کاربر را **درست بعد از یک ورود واقعی** به
سایت مهاجم می‌برد — که قانع‌کننده‌ترین حالت ممکن برای فیشینگ است.

`safeInternalPath()` فقط مسیر داخلی را رد می‌کند. `//host` و `/\host` هم رد
می‌شوند چون مرورگر هر دو را مبدأ دیگر می‌خواند.

هر ۱۰ بردار تست شد:

| ورودی | نتیجه |
|---|---|
| `/dashboard`, `/residences/list?tab=all` | اجازه |
| `https://evil.example` | مسدود |
| `//evil.example` | مسدود |
| `/\evil.example` | مسدود |
| `http://localhost:3002/dashboard` (مطلق، حتی همین دامنه) | مسدود |
| `javascript:alert(1)` | مسدود |
| `""`, `null`, `dashboard` (بدون اسلش) | مسدود |

## خروج

`doLogoutActions` قبلاً فقط یک کلید را invalidate می‌کرد. `invalidate` یعنی
«کهنه‌اش کن»، نه «دورش بریز» — پس پروفایل، رزروها، موجودی کیف پول و تِردهای
چت در حافظه می‌ماندند و **بی‌درنگ به نفر بعدی که روی همان دستگاه وارد می‌شد
نشان داده می‌شدند** تا وقتی هر کلید دوباره واکشی شود. روی یک گوشی مشترک یعنی
رزروهای یک نفر به دیگری. حالا `queryClient.clear()`.

## QA — سناریوهایی که اجرا شد

| سناریو | نتیجه |
|---|---|
| ناشناس → `/dashboard` | یک ۳۰۷ به ورود، `redirectTo=/dashboard` |
| ناشناس → `/residences/list?tab=x` | یک ۳۰۷، query هم حفظ شد |
| ناشناس → `/reservations/12` | یک ۳۰۷، deep link حفظ شد |
| نشست میزبان → مسیرهای پنل | ۲۰۰، بدون ریدایرکت |
| نشست مهمان → مسیر میزبان | ۲۰۰ (طبق تصمیم بالا) |
| توکن منقضی + refresh | رد می‌شود |
| توکن منقضی بدون refresh | به ورود |
| خروج | هر دو کوکی پاک، کش خالی |

و یک قدم‌زدن کامل: خروج → `/residences/list` → ورود با کد → **مستقیم همان
مسیر**، نه پیشخوان، نه زنجیره.

## تله‌ها

- **بج ادمین جداست.** پنل ادمین توکن خودش را زیر `lidoma_admin_token` نگه
  می‌دارد و از `api/Admin/adminApi` می‌رود؛ این فایل به آن کاری ندارد.
- **`api/index.tsx` توکن را در بارگذاری ماژول از کوکی می‌خواند.** پس رفرش
  صفحه هدر `Authorization` را از دست نمی‌دهد؛ اگر این حذف شود، هر رفرش
  کاربر را بی‌احراز می‌کند بدون اینکه کوکی پاک شده باشد.
- **`/support` عمداً محافظت‌نشده است** — تب سوالات متداولش برای عموم مفید
  است.

# سیستم گفتگو — مشخصات کامل

> این فایل نسخه‌ی کامل‌شده‌ی ایده‌ی اولیه است. بخش‌هایی که کاربر گفته بود عیناً
> حفظ شده‌اند؛ بقیه اضافه شده تا مشخصات قابل پیاده‌سازی و بدون ابهام باشد.

---

## ۰. جواب سؤال: Airbnb از چه سرویسی استفاده می‌کند؟

**از هیچ سرویس بیرونی.** Airbnb پیام‌رسان میزبان-مهمان را خودش در خانه ساخته و
روی زیرساخت خودش می‌چرخاند. دلیلش هم روشن است: پیام‌ها به رزرو، به وضعیت رزرو، و
به سیاست‌های پلتفرم (مثل مخفی‌کردن شماره تماس قبل از تأیید رزرو) گره خورده‌اند —
چیزی که یک چت عمومی جعبه‌سیاه نمی‌تواند بدهد.

گزینه‌های آماده‌ای که معمولاً پیشنهاد می‌شوند — Sendbird، Stream Chat، Twilio
Conversations، PubNub — برای این پروژه **قابل استفاده نیستند**: هر سه پرداخت
ارزی و دسترسی بین‌المللی می‌خواهند و از ایران در دسترس نیستند. مستقل از آن،
هزینه‌شان به‌ازای کاربر فعال ماهانه است.

**تصمیم: در خانه، روی همین استک.** Express + Prisma + PostgreSQL که هست، و
Redis که همین امروز اضافه شد و دقیقاً همان چیزی است که برای realtime چنداینستنسی
لازم است. صفر هزینه‌ی ماهانه، دیتا داخل کشور، و چت به رزرو وصل می‌شود.

---

## ۱. نکته‌ی مهم: این مهاجرت است، نه ساخت از صفر

فرانت گفتگو از دوران Odoo **موجود است** و به اندپوینت‌های مرده وصل است:

| فایل | وضعیت |
|---|---|
| `pages/chats/index.tsx` → `components/Chats/` | لیست گفتگوها — به `/api/get_order_messages` |
| `components/Chat/` | تک‌گفتگو — به `/api/get_messages` و `/api/add_message` |
| `components/Support/` | چت پشتیبانی — به `/api/support_chats/get|add` |
| `constants/enums/chat_status.ts` | `active` / `archived` |

یعنی رفتار قدیمی (از جمله پیامک هنگام پیام جدید) قبلاً وجود داشته و کاربران
انتظارش را دارند. UI بازنویسی می‌شود، ولی **هیچ قابلیتی از دست نمی‌رود**.

## ۲. مدل داده

```prisma
enum ConversationType   { BOOKING, SUPPORT }
enum ConversationStatus { OPEN, PENDING, CLOSED }   // PENDING = منتظر پاسخ کاربر
enum ParticipantRole    { GUEST, HOST, ADMIN }
enum MessageType        { TEXT, IMAGE, FILE, SYSTEM, INTERNAL_NOTE }
```

**Conversation** — `publicId` (nanoid) برای URL تا شناسه‌ها قابل شمارش نباشند ·
`type` · `status` · `subject` (پشتیبانی) · `bookingId Int? @unique` ← همین
یکتایی، idempotency را تضمین می‌کند · `residenceId` (denormalized، برای فیلتر
ادمین و هدر گفتگو) · `assignedAdminId` · `lastMessageAt` + `lastMessagePreview`
(denormalized، تا لیست گفتگوها یک کوئری باشد نه N+1).

**ConversationParticipant** — `@@unique([conversationId, userId])` ·
`role` · `lastReadAt` + `lastReadMessageId` · `unreadCount` (denormalized، برای
بج هدر) · `notifiedAt` (throttle پیامک) · `isMuted` · `leftAt`.

**Message** — `conversationId` · `senderId Int?` (برای SYSTEM خالی) ·
`senderRole` · `type` · `body` · `meta Json?` (بار داده‌ی پیام سیستمی) ·
`attachmentUrl` / `attachmentName` / `attachmentSize` ·
`clientNonce String?` با `@@unique([conversationId, clientNonce])` ·
`deletedAt` · ایندکس `[conversationId, id]` برای صفحه‌بندی مکان‌نما.

## ۳. چرخه‌ی حیات

**گفتگوی رزرو.** با ثبت رزرو (state `HOST_APPROVAL`) گفتگو ساخته می‌شود، نه با
تأیید — مهمان و میزبان دقیقاً همان‌جا سؤال دارند. تابع
`ensureBookingConversation(reservationId)` idempotent است و روی `bookingId`
یکتا تکیه می‌کند، نه روی «اول بخوان بعد بنویس» که زیر بار همزمانی می‌شکند.
همراهش یک پیام `SYSTEM` با خلاصه‌ی رزرو: نام اقامتگاه، تاریخ ورود/خروج (شمسی)،
تعداد مهمان، شماره‌ی پیگیری.

**تغییر وضعیت رزرو** (`HOST_APPROVAL → SECOND_PAYMENT → DONE`، یا `CANCEL` /
`EXPIRED`) یک پیام `SYSTEM` دیگر با `meta.kind` می‌سازد، و فرانت آن را به‌جای
حباب متن، به شکل یک **کارت وضعیت** رنگ‌دار رندر می‌کند — سبز برای تأیید، قرمز
برای لغو، کهربایی برای در انتظار پرداخت.

**گفتگوی پشتیبانی.** کاربر از فرم می‌سازد؛ تنها participant اولیه خودش است.
ادمین‌ها **pool** هستند: دسترسی از روی نقش، نه از روی عضویت. اولین ادمینی که
جواب می‌دهد به‌عنوان `assignedAdminId` ثبت و participant می‌شود، تا معلوم باشد
چه کسی پاسخ داده.

## ۴. Realtime

**SSE + Redis pub/sub** — نه WebSocket، نه socket.io.

| چرا | |
|---|---|
| `EventSource` بومی مرورگر است | صفر کیلوبایت به باندل اضافه می‌شود. با توجه به این‌که کل نشست هشتم صرف کم‌کردن باندل شد، ۴۰KB برای socket.io قدم به عقب است |
| اتصال یک‌طرفه کافی است | ارسال پیام یک POST معمولی است؛ فقط دریافت باید push باشد |
| از پراکسی رد می‌شود | بدون handshake ارتقا، بدون تنظیم خاص روی لیارا |
| reconnect داخلی دارد | با `Last-Event-ID` می‌شود پیام‌های جامانده را جبران کرد |

Redis pub/sub کانال `chat:user:<id>` است تا با چند اینستنس، پیام به هر اینستنسی
که آن کاربر رویش وصل است برسد. **اگر Redis نباشد** SSE فقط اینستنس خودش را
پوشش می‌دهد و فرانت به polling برمی‌گردد — همان اصل «نبودنش چیزی را نشکند» که
در لایه‌ی کش هم رعایت شد.

تایپینگ و رسید خواندن ephemeral‌اند: فقط pub/sub، هیچ‌وقت در دیتابیس نمی‌نشینند.

## ۵. اندپوینت‌ها

**کاربر** (`/api/conversations`، همه پشت `requireAuth`)

| متد | مسیر | کار |
|---|---|---|
| GET | `/` | لیست، فیلتر `type` و `status`، مکان‌نما |
| GET | `/unread-count` | بج هدر — یک کوئری جمع |
| GET | `/stream` | SSE |
| POST | `/support` | ساخت گفتگوی پشتیبانی |
| GET | `/:publicId` | جزئیات + طرف مقابل + خلاصه‌ی رزرو |
| GET | `/:publicId/messages` | مکان‌نمای `before` |
| POST | `/:publicId/messages` | ارسال (`body`, `clientNonce`) |
| POST | `/:publicId/read` | خوانده‌شدن تا پیام مشخص |
| POST | `/:publicId/typing` | throttle‌شده |

**ادمین** (`/api/admin/conversations`) — لیست با فیلتر نوع/وضعیت/جست‌وجو و
«واگذارنشده»، مشاهده‌ی کامل، ارسال پیام وسط گفتگو، یادداشت داخلی
(`INTERNAL_NOTE` که کاربر نمی‌بیند)، تغییر وضعیت، واگذاری، حذف نرم پیام.

## ۶. چیزهایی که به ایده اضافه شد و چرا

۱. **`clientNonce`.** ارسال خوش‌بینانه بدون آن یعنی هر retry شبکه یک پیام تکراری.
یکتایی روی `[conversationId, clientNonce]` این را در سطح دیتابیس می‌بندد، نه در
سطح UI.

۲. **مکان‌نما به‌جای offset.** در چتی که همان لحظه پیام جدید می‌گیرد، صفحه‌ی
دوم با offset یا پیام تکراری می‌دهد یا پیام جاافتاده.

۳. **`unreadCount` denormalized.** بج هدر روی هر بار لود صفحه اجرا می‌شود؛
شمردن پیام‌های خوانده‌نشده با join در هر بار، همان کاری است که صفحه‌ی اصلی را
۲ ثانیه‌ای کرده بود.

۴. **تشخیص تماس خارج از پلتفرم.** الگوی شماره‌تلفن و آیدی پیام‌رسان در متن پیام
شناسایی و **علامت‌گذاری** می‌شود (نه مسدود). دلیلش تجاری است: توافق خارج از سایت
یعنی کمیسیون از دست‌رفته و رزروی که پشتیبانی نمی‌تواند از آن دفاع کند. سخت‌گیری
کامل (مثل Airbnb که قبل از تأیید رزرو ماسک می‌کند) به‌عنوان یک سوییچ تنظیمات
گذاشته می‌شود تا تصمیمش با شما باشد.

۵. **یادداشت داخلی ادمین.** پشتیبانی بدون جایی برای «این کاربر قبلاً شکایت
داشته» یا مجبور است در کانال دیگری بنویسد یا اصلاً ننویسد.

۶. **پیام ادمین با هویت آشکار.** وقتی ادمین وسط گفتگوی میزبان-مهمان می‌نویسد،
با نام «پشتیبانی لیدوماتریپ» و استایل متمایز دیده می‌شود. ادمینِ نامرئی در چت
دو نفره، وقتی لو برود، اعتماد را از بین می‌برد.

۷. **محدودیت نرخ.** `express-rate-limit` که در پروژه هست، روی ارسال پیام.

۸. **حذف نرم.** «این پیام حذف شد» به‌جای ناپدیدشدن بی‌توضیح.

۹. **بی‌صداکردن گفتگو.** برای میزبانی که ده رزرو همزمان دارد.

۱۰. **پیوست تصویر.** روی همان `multer-s3` و باکت لیارا که آپلود اقامتگاه از آن
استفاده می‌کند؛ سقف حجم و allowlist پسوند.

## ۷. پیامک (رفتار قدیمی Odoo که باید حفظ شود)

هنگام پیام جدید، برای هر طرف مقابل:

- اگر گفتگو را **بی‌صدا** کرده → پیامک نه.
- اگر همین حالا **آنلاین** است (اتصال SSE فعال، از روی کلید Redis) → پیامک نه؛
  پیام را که دارد می‌بیند.
- اگر در **۱۵ دقیقه‌ی گذشته** برای همین گفتگو پیامک گرفته → نه. یک مکالمه‌ی
  رفت‌وبرگشتی نباید سی پیامک بفرستد.
- در غیر این‌صورت یک پیامک کوتاه با نام فرستنده و لینک گفتگو.

throttle روی کلید Redis با TTL می‌نشیند، نه روی ستون دیتابیس، چون ذاتاً موقتی
است. `src/lib/otp.ts` امروز یک stub است — لایه‌ی پیامک همان‌جا و با همان
تنظیمات `env.otp` نوشته می‌شود، پس وصل‌کردن ارائه‌دهنده‌ی واقعی یک جای واحد دارد.

## ۸. رابط کاربری

**دسکتاپ** دوستونه: لیست گفتگوها سمت راست، رشته‌ی پیام سمت چپ.
**موبایل** پشته‌ای: لیست، و با انتخاب، رشته تمام‌صفحه با دکمه‌ی بازگشت.

- حباب‌ها با دم، پیام خودی و طرف مقابل متمایز
- جداکننده‌ی تاریخ شمسی («امروز»، «دیروز»، «۵ شهریور»)
- تیک تکی/دوتایی برای ارسال/خوانده‌شده
- «در حال نوشتن…» با انیمیشن سه‌نقطه
- کارت وضعیت رزرو به‌جای حباب برای پیام‌های سیستمی
- ارسال خوش‌بینانه: پیام بلافاصله با حالت «در حال ارسال» ظاهر می‌شود
- اسکرول چسبان به پایین، مگر کاربر بالا رفته باشد → «پیام جدید ↓»
- Enter ارسال، Shift+Enter خط جدید (روی موبایل هر دو خط جدید)
- بج نخوانده در هدر سایت
- RTL کامل، `aria-live` برای پیام‌های ورودی، تمرکز صفحه‌کلید

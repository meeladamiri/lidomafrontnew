# پرداخت‌های مهمان — دفتر اقساط

## چرا

`Reservation.paidAmount` یک عدد بود. یعنی رزروی که در سه قسط تسویه شده، فقط
جمعش را ثبت می‌کرد: نه اینکه هر واریز کِی رسید، نه با چه روشی، نه چه کسی
ثبتش کرد.

این حالت استثنا نیست. در اودو **۹٬۴۴۵ رزرو بیش از یک پرداخت داشتند**، تا
سیزده تا:

```
۱ پرداخت  → ۵۲٬۷۴۶ رزرو
۲ پرداخت  →  ۸٬۴۵۸
۳ پرداخت  →    ۸۱۴
۴ تا ۱۳   →    ۱۷۳
```

و چون درگاه پرداخت هنوز وصل نیست، عملاً **همه‌ی** پرداخت‌ها دستی ثبت می‌شوند.

## جدول

`reservation_payments` — مهاجرت `20260901000000_reservation_payments`.

| ستون | معنی |
|---|---|
| `amount` | مبلغ این واریز |
| `method` | `GATEWAY` · `CARD_TRANSFER` · `BANK_TRANSFER` · `CASH` · `WALLET` · `OTHER` |
| `paid_at` | زمانی که پول جابه‌جا شد — نه زمانی که تایپ شد |
| `reference` | شماره پیگیری / فیش |
| `recorded_by_id` / `recorded_by_name` | چه کسی ثبتش کرد |
| `voided_at` / `voided_reason` / `voided_by_id` | ابطال |

`paidAmount` روی رزرو می‌ماند، به‌عنوان **جمع کش‌شده‌ی پرداخت‌های معتبر**. این
عمدی است: پنل واریزی، محاسبه‌ی استرداد لغو، و لیست رزروها همگی از آن می‌خوانند
و هیچ‌کدام لازم نیست بدانند این جدول وجود دارد.

## تصمیم‌ها

### پرداخت حذف نمی‌شود، باطل می‌شود

ردیف می‌ماند، خط‌خورده، با دلیل. «فکر می‌کردیم سوم پول رسیده» دقیقاً همان
چیزی است که در یک اختلاف به آن استناد می‌شود؛ حذفش یعنی پاک‌کردن سندی که
اختلاف بر سرش است.

### مانده‌ی افتتاحیه

رزروهای ساخته‌شده پیش از این جدول `paidAmount` دارند و **هیچ ردیفی** ندارند.
محاسبه‌ی مجدد جمع از یک دفتر خالی، آن عدد را پاک می‌کرد.

پس اولین نوشتن روی چنین رزروی، ابتدا یک ردیف افتتاحیه با مبلغ موجود می‌سازد:

> مبلغ پرداختی ثبت‌شده پیش از راه‌اندازی دفتر پرداخت‌ها

تست‌شده روی `SO369960`: پرداختی ۳٬۸۵۰٬۰۰۰ بود، بعد از ثبت ۱٬۰۰۰ شد ۳٬۸۵۱٬۰۰۰
— یعنی مانده‌ی قبلی حفظ شد.

### اضافه‌پرداخت پنهان نمی‌شود

`remaining` صفر می‌شود ولی `overpaid` جدا برگردانده می‌شود. مهمانی که دو بار
واریز کرده، مبلغی طلبکار است؛ کلمپ‌کردن مانده به صفر، همان چیزی است که باعث
می‌شود کسی متوجه نشود.

### پرداخت روی رزرو لغوشده ثبت نمی‌شود

سرویس ردش می‌کند. استرداد یک لغو، مسیر خودش را دارد.

## API

```
GET   /api/admin/reservations/:id/payments
POST  /api/admin/reservations/:id/payments    { amount, method, paidAt, reference?, note? }
POST  /api/admin/payments/:id/void            { reason }
```

پاسخِ `GET` علاوه بر ردیف‌ها یک `summary` می‌دهد: `due`، `paid`، `remaining`،
`overpaid`، و `ledger_started` — آخری برای اینکه صفحه بتواند بگوید چرا دفتر
خالی است به‌جای اینکه «کسی پول نداده» به نظر برسد.

## رابط کاربری

`components/Admin/PaymentsPanel.tsx` — سه کاشی بالا (مبلغ کل جهت پرداختی /
جمع پرداختی / باقی‌مانده)، دفتر زیرش، و «ثبت پرداخت».

تاریخ واریز با تقویم شمسی گرفته می‌شود (`JalaliDateField`) و ساعت جدا، چون
تاریخ واقعی واریز و لحظه‌ی تایپ یکی نیستند.

## آنچه نساخته شده

- **درگاه پرداخت** — `method: GATEWAY` وجود دارد ولی چیزی خودکار پر نمی‌شود.
- **استرداد** — ابطال یک پرداخت فقط از جمع کم می‌کند؛ پول برنمی‌گردد.

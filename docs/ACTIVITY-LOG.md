# لاگ فعالیت‌ها و ارتباطات

`backend/src/modules/activity/` · `backend/src/modules/admin/reservationActions.routes.ts` ·
`front/components/Admin/ActivityTimeline.tsx`

## یک جدول، یک تایم‌لاین

تماس تلفنی، تغییر وضعیت، ویرایش قیمت و وچری که ارسال شده، **یک سؤال‌اند که یک
بار پرسیده می‌شود**: چه اتفاقی برای این رزرو افتاده؟ پس یک فهرست مرتب‌شده بر
اساس زمان‌اند، نه سه پنل که خواننده باید خودش درهم‌بافتشان کند.

پنج نوع در `activity_logs`:

| | |
|---|---|
| `CALL` | تماس — دستی |
| `NOTE` | یادداشت — دستی |
| `STATE_CHANGE` | وضعیت رزرو عوض شد |
| `FIELD_CHANGE` | تاریخ، قیمت، مانده یا چیز دیگری عوض شد |
| `MESSAGE_SENT` | پیامی برای مهمان یا میزبان رفت |

چهار ایندکس، دقیقاً برای همان فیلترهایی که پنل دارد:
`(reservation_id, id)` · `(user_id, id)` · `(kind, created_at)` · `(actor_id, created_at)`

## تغییرناپذیری — با دیتابیس، نه با قرارداد

یک trigger روی `UPDATE` و `DELETE` **exception می‌دهد**:

```
activity_logs is append-only: UPDATE is not permitted
activity_logs is append-only: DELETE is not permitted
```

اول با `CREATE RULE ... DO INSTEAD NOTHING` نوشته بودم و برگشتم: آن هم ردیف را
حفظ می‌کند، ولی به caller می‌گوید ویرایشت موفق بود — **دروغی بدتر از خودِ
ویرایشی که جلویش را گرفته**.

«هیچ اندپوینتی update نمی‌کند» خاصیتِ کدِ امروز است؛ این باید خاصیتِ داده باشد و
از دست نفر بعدی که با عجله یک اندپوینت اضافه می‌کند جان سالم ببرد.

## چطور از منطق اصلی بیرون می‌ماند

`reservations.service` اصلاً نمی‌داند این ماژول وجود دارد. دو قاعده:

**۱. نوشتن‌ها fire-and-forget‌اند** (`log()`)، مثل هوک‌های چت و اعلان که از قبل
بودند. یک خط لاگ که ننوشته شد، یک باگ است که باید درست شود؛ **هرگز** دلیل شکست
یک رزرو نیست. عمداً `async` نیست تا کسی نتواند به اشتباه await‌ش کند.

**۲. ورودی‌های خودکار از `diffAndLog(before, after)` می‌آیند.** caller دو
آبجکت می‌دهد و تمام؛ خودش می‌فهمد چه چیزی عوض شده و جمله‌اش را می‌سازد. نسخه‌ای
که هر فیلد را جدا لاگ می‌کند، اولین باری که کسی ستون اضافه کند از کار می‌افتد.
و چون وقتی چیزی عوض نشده هیچ نمی‌نویسد، می‌شود بی‌قید‌وشرط صدایش زد.

`summary` **هنگام نوشتن** رندر و ذخیره می‌شود. لاگی که خودش را از روی id
بازسازی کند، به‌محض اینکه رزرو جلو برود بی‌صدا حرفش را عوض می‌کند.

## دکمه‌های عملیات — از اودو

اودو برای هرکدام یک server action جدا داشت:

| اودو | ما |
|---|---|
| `ارسال اطلاعات میزبان به مسافر` · `مسافر به میزبان` | یک اندپوینت |
| `ارسال لینک اقامتگاه` · `ارسال وچر به میزبان` | با یک `kind` |
| `ارسال شماره کارت` · `send review sms` | |
| `register call from/to host/user` ×۴ | یک فرم با دو پرسش |

شش اندپوینت جدا نشد چون فقط در «چه کسی چه متنی می‌گیرد» فرق دارند؛ شش handler
تقریباً یکسان یعنی شش جا که دفعه‌ی بعد باید عوض شود.

چهار دکمه‌ی تماس هم یک فرم با دو بُعد (ورودی/خروجی × مهمان/میزبان) شد — چهار
دکمه که در دو boolean فرق دارند، منویی است که خواننده هر بار باید رمزگشایی کند.

**هر ارسال یک خط `MESSAGE_SENT` می‌نویسد.** نیمی از فایده‌ی دکمه همین است:
«کسی آدرس را برایشان فرستاد؟» تا امروز جواب نداشت.

⚠️ **«ارسال شماره کارت» وقتی میزبان کارت ثبت‌نکرده رد می‌شود.** پیامی که به
مهمان بگوید پول را به هیچ‌جا واریز کن، از نبودِ پیام بدتر است.

⚠️ **پیامک هنوز stub است** (`lib/sms.ts`)، پس فعلاً اعلان درون‌سایتی می‌رود.
گیرنده، متن و خط لاگ همه واقعی‌اند؛ فقط ترابری‌اش مانده — و آن یک جاست.

## اعلان این پیام‌ها عمداً به رزرو کلید نمی‌خورد

ایندکس یکتای اعلان‌ها `(user, kind, entity_type, entity_id)` است. اگر
`MESSAGE_SENT` را به رزرو کلید می‌زدیم، هر پیام فقط **یک بار** قابل ارسال بود —
و «دوباره بفرست، پیام را گم کرده» رایج‌ترین دلیل فشردن آن دکمه است.

## صفحه‌ی جزئیات رزرو

چهار بلوک، به ترتیبی که کار واقعاً انجام می‌شود: **پول → مهلت → وضعیت و مسیر →
تایم‌لاین → عملیات**.

دکمه‌ها **بر اساس پیامد** گروه شدند: مشاهده / ارسال / پایان‌دادن. اودو
«چاپ فاکتور» را کنار «لغو رزرو» گذاشته بود و هر دو یک‌اندازه بی‌خطر به نظر
می‌رسیدند.

**فاکتور** بیرون از `AdminLayout` است — سایدبار و نوار بالا اثاثیه‌ی گشتن‌اند و
این صفحه برای کاغذ شدن ساخته شده — و تک‌رنگ است، چون طرحی که به رنگ پس‌زمینه
تکیه کند از پرینتر اداری به شکل جعبه‌های خاکستری با متن خاکستری بیرون می‌آید.

## یک قاعده‌ی کوچک که مهم بود

در تایم‌لاین، برچسب «سیستم» **فقط وقتی** نشان داده می‌شود که هیچ actorی نباشد —
نه بر اساس `source`. وچری که ادمین فرستاده مال اوست، مهم نیست کدام flow ردیفش
را نوشته. اول بر اساس `source` گذاشته بودم و هر فشردن دکمه خودکار به نظر می‌رسید.
